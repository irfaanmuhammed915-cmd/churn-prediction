# 📡 Customer Churn Prediction

> **XGBoost classifier with SHAP explainability** — predicts which telecom customers are likely to churn, and *why*.  
> Live Streamlit app · 0.81 AUC-ROC · 20/20 tests passing

---

## 🎯 Problem Statement

Telecom companies lose 15–30% of their customers annually to churn. Acquiring a new customer costs **5–7× more** than retaining an existing one. This project builds a machine learning system that:

1. **Predicts** which customers are at risk of churning (binary classification)
2. **Explains** the prediction per-customer using SHAP values
3. **Deploys** the model as an interactive Streamlit app for business analysts

## ⚙️ How It Works

### 1. Feature Engineering

Four engineered features on top of the raw 19 telecom fields:

| Feature | Formula | Business Logic |
|---|---|---|
| `ChargesPerMonth` | `TotalCharges / tenure` | Normalises spending by customer loyalty |
| `NumAddOns` | Count of 6 value-added services | More services → higher switching cost → lower churn |
| `HasFiberAndNoSecurity` | `(Fiber internet) AND (no security add-on)` | High-risk combination in the data |
| `IsMonthToMonth` | Binary contract flag | Month-to-month customers churn at ~3× the rate of 2-year customers |

### 2. Preprocessing Pipeline

Built with `sklearn.pipeline.Pipeline`:
- **Numerical features** → `StandardScaler`
- **Categorical features** → `OneHotEncoder` (handle_unknown="ignore")
- `ColumnTransformer` combines both

### 3. Model — XGBoost

```python
XGBClassifier(
    n_estimators=400,
    max_depth=5,
    learning_rate=0.05,
    subsample=0.8,
    colsample_bytree=0.8,
    scale_pos_weight=2.35,   # handles class imbalance
)
```

`scale_pos_weight` is computed as `n_negative / n_positive` from the training set, handling class imbalance without resampling.

### 4. Explainability — SHAP

Every prediction is explained using `shap.TreeExplainer`, which decomposes the model output into per-feature contributions. The app shows a waterfall bar chart for each scored customer.

Top churn drivers found by SHAP:

| Rank | Feature | Direction |
|---|---|---|
| 1 | Contract = Month-to-month | ↑ Churn |
| 2 | Tenure (short) | ↑ Churn |
| 3 | Internet = Fiber optic | ↑ Churn |
| 4 | Online Security = No | ↑ Churn |
| 5 | Monthly Charges (high) | ↑ Churn |

## 💡 Key Design Decisions

**Why XGBoost over Logistic Regression?**  
Logistic regression assumes linear relationships between features and log-odds, which misses interaction effects (e.g. Fiber internet without security being disproportionately risky). XGBoost captures these nonlinear interactions while remaining interpretable via SHAP.

**Why SHAP instead of feature importances?**  
Built-in XGBoost feature importances (gain, cover) are global. SHAP gives *per-prediction* explanations, which matter in a business context — an analyst needs to explain *why this specific customer* was flagged, not just which features matter on average.

**Why `scale_pos_weight` instead of SMOTE?**  
SMOTE introduces synthetic samples that can distort the decision boundary. `scale_pos_weight` achieves the same objective (penalising misclassification of the minority class) without modifying the training data.
